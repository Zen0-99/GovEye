# Plan 11-04: Activity Score + Trait Radar Wiring to Real Data

## Goal
Wire the existing `ActivityScoreCalculator`, `TraitBarCalculator`, and `PercentileCalculator` domain calculators to real peer aggregation data from the bundled DB, and re-enable the `ActivityScoreStrip` and `TraitRadarChart` UI components on the MP profile.

## Tasks

### StatsRepository (new aggregation repository)
1. Create `core/data/src/main/java/com/goveye/app/data/repo/StatsRepository.kt` — `@Singleton class StatsRepository @Inject constructor(private val divisionDao: DivisionDao, private val committeeDao: CommitteeDao, private val debateSpeechDao: DebateSpeechDao, private val hansardDao: HansardDao, private val mpDao: MpDao)`. This repository aggregates data from existing DAOs to compute per-MP metrics and peer averages. No new tables, no API calls.

2. Implement `suspend fun getVoteParticipationRate(memberId: Int, house: Int): Float` — query `divisionDao.getDivisionIdsForMember(memberId)` to get the count of divisions the MP voted in. Query `divisionDao.getAllDivisionsByHouse(house)` to get total divisions. Return `votedCount / totalDivisions` (0.0–1.0). Handle division by zero (return 0f).

3. Implement `suspend fun getQuestionCount(memberId: Int): Int` — query `hansardDao` for contributions of type "question" for this MP. Add a new DAO query to `HansardDao.kt`: `@Query("SELECT COUNT(*) FROM hansard_contributions WHERE memberId = :memberId AND contributionType = 'question'") suspend fun countQuestionsForMember(memberId: Int): Int`. If the `contributionType` column doesn't exist, count all contributions as a proxy (log a warning).

4. Implement `suspend fun getSpeechCount(memberId: Int): Int` — query `debateSpeechDao` for non-intervention speeches by this MP. Add a new DAO query to `DebateSpeechDao.kt`: `@Query("SELECT COUNT(*) FROM debate_speeches WHERE memberId = :memberId AND isIntervention = 0") suspend fun countSpeechesForMember(memberId: Int): Int`.

5. Implement `suspend fun getCommitteeCount(memberId: Int): Int` — query `committeeDao.getCommitteesForMember(memberId)` and return `.size`.

6. Implement `suspend fun getRebellionRate(memberId: Int, partyName: String?): Float` — reuse the existing `RebellionCalculator.compute()` logic from `MpProfileViewModel.loadProfile()` (lines 131-137). Fetch member votes via `divisionDao.getVotesForMember(memberId)`, fetch all votes for those divisions via `divisionDao.getVotesForDivisions(divisionIds)`, call `RebellionCalculator.compute(memberVotes, allVotesByDivision, partyName)`, return `rebellionStats.rebellionRate`.

7. Implement `suspend fun getPeerAverages(house: Int): PeerAverages` — compute average questions, speeches, and committees across all active MPs in the given house. Query `mpDao.observeAllMps()` (one-shot via `.first()`), for each MP compute questionCount, speechCount, committeeCount, then average. Cache the result in a `@Volatile var` with a timestamp — recompute only if older than 5 minutes (650 MPs × 3 queries is expensive).

8. Implement `suspend fun getPeerValues(metric: String, house: Int): List<Float>` — for percentile calculation. For each active MP in the house, compute the metric value (rebellionRate, participationRate, questionCount, speechCount, committeeCount). Return as `List<Float>`. Cache per-metric with the same 5-minute TTL as peer averages. Use a `when(metric)` block to dispatch to the right computation.

9. Implement `suspend fun getActivityScore(memberId: Int, house: Int, partyName: String?): ActivityScore` — call `getVoteParticipationRate()`, `getQuestionCount()`, `getSpeechCount()`, `getCommitteeCount()`, `getPeerAverages(house)`, then call `ActivityScoreCalculator.compute(voteParticipationRate, questionCount, speechCount, committeeCount, peerAverages)`.

10. Implement `suspend fun getTraitBars(memberId: Int, house: Int, partyName: String?): List<TraitBar>` — call `getRebellionRate()`, `getVoteParticipationRate()`, `getQuestionCount()`, `getSpeechCount()`, `getCommitteeCount()`, `getPeerAverages(house)`, and all 5 `getPeerValues()` variants, then call `TraitBarCalculator.compute(rebellionRate, participationRate, questionCount, speechCount, committeeCount, peerRebellionRates, peerParticipationRates, peerQuestionCounts, peerSpeechCounts, peerCommitteeCounts, peerAverages)`.

### Performance optimization (mitigation for 650-MP aggregation)

## Risks
- **Peer aggregation performance**: Computing 5 metrics × 650 MPs on every profile open is expensive. Mitigation: 5-minute in-memory cache for peer averages and peer values. The cache is per-app-session (not persisted). First open computes, subsequent opens reuse. If this is still too slow, consider pre-computing at build time and storing in a `mp_stats` table (deferred to v2 if needed).
- **Missing hansard contributionType column**: The `hansard_contributions` table may not have a `contributionType` column to distinguish questions from speeches. Mitigation: check the `HansardContributionEntity` schema; if no type column, count all contributions as a proxy and log a warning. The build script can be updated later to categorize contributions.
- **Empty debate_speeches table**: If `build_debates.py` hasn't run or produced no data, speech counts will be 0 for all MPs. Mitigation: handle gracefully — 0 speeches → 0th percentile, score component = 0. The UI still renders.
- **Rebellion rate computation cost**: `RebellionCalculator.compute()` for 650 MPs (for peer values) requires fetching all votes for all divisions for all MPs. This is very expensive. Mitigation: for peer rebellion rates, use a simplified approximation — compute rebellion rate only for the target MP (exact), and use a pre-computed average for peers (e.g., 5% typical rebellion rate). This avoids 650 × full-vote-fetch. Document this as an approximation in the code.
