# Plan 11-05: Party Manifestos Build Script + FTS Tables + Workflow

## Goal
Download plain-text manifestos for 7 major UK parties from Lancaster Wmatrix, store in a `party_manifestos` table with dual FTS4/FTS5 virtual tables in the bundled DB, and set up a monthly GitHub Actions workflow to check for updates.

## Tasks

### Build script (goveye-data repo)
1. Create `goveye-data/build_manifestos.py` following the per-API build script pattern from `build_mps.py` — seed/delta modes, schema validation against `schemas/bundled_schema.json`.

2. Define the Lancaster Wmatrix base URL: `https://ucrel.lancs.ac.uk/wmatrix/ukmanifestos2024/`. Define the party ID mapping (from `mps.db`):
   ```python
   PARTY_MANIFESTOS = {
       4:    {"abbrev": "Con",    "filename": "conservative_2024.txt"},
       15:   {"abbrev": "Lab",    "filename": "labour_2024.txt"},
       17:   {"abbrev": "LD",     "filename": "libdem_2024.txt"},
       44:   {"abbrev": "Green",  "filename": "green_2024.txt"},
       22:   {"abbrev": "PC",     "filename": "plaidcymru_2024.txt"},
       29:   {"abbrev": "SNP",    "filename": "snp_2024.txt"},
       1036: {"abbrev": "RUK",    "filename": "reformuk_2024.txt"},
   }
   ```
   The exact filenames on Lancaster Wmatrix need to be verified — implement a `discover_manifesto_url(party_abbrev: str) -> str` function that tries common URL patterns and falls back to party website PDFs.

3. Implement `download_manifesto(party_id: int, url: str) -> str` — download the plain-text file. If it's a PDF (from party website fallback), extract text using `pdfplumber` or `PyPDF2` (add to `requirements.txt`). Return the text content.

4. Implement `compute_word_count(text: str) -> int` — split on whitespace, return `len(text.split())`.

5. Implement `build_manifestos_tables(conn)` — create three tables:
   ```sql
   CREATE TABLE party_manifestos (
       partyId INTEGER PRIMARY KEY,
       manifestoText TEXT NOT NULL,
       manifestoYear INTEGER NOT NULL,
       wordCount INTEGER NOT NULL,
       source TEXT
   );
   CREATE VIRTUAL TABLE party_manifestos_fts4 USING fts4(manifestoText, content='party_manifestos');
   CREATE VIRTUAL TABLE party_manifestos_fts5 USING fts5(manifestoText, content='party_manifestos');
   ```
   Note: FTS virtual tables are created with raw `execSQL` in the build script, NOT via Room annotations. Room will manage them as external content tables.

6. Implement `insert_manifesto(conn, party_id: int, text: str, year: int, source: str)` — insert into `party_manifestos`, then populate both FTS tables by inserting the text into `party_manifestos_fts4` and `party_manifestos_fts5` (or rely on contentless FTS triggers if supported).

7. Implement seed mode: download all 7 manifestos, insert into tables.
8. Implement delta mode: copy previous DB, download all manifestos, compare text hash (`hashlib.sha256(text.encode()).hexdigest()`) with previous — only upsert if changed. If no changes, skip (manifestos change rarely — only at general elections).
9. Set `TABLE_NAMES = ["party_manifestos", "party_manifestos_fts4", "party_manifestos_fts5"]` for `diff_db.py` and `manifest.py` compatibility. Note: `diff_db.py` may need special handling for FTS virtual tables (they can't be diffed like regular tables — treat as full-replace, not row-level diff).

### GitHub Actions workflow
25. Create `goveye-data/.github/workflows/update-manifestos.yml` following `update-interests.yml` pattern with these differences:
    - Cron: `0 1 1 * *` (D-03: monthly, 1st of month at 01:00 UTC — manifestos change rarely)
    - Build command: `python build_manifestos.py --output manifestos.db --schema schemas/bundled_schema.json --mode seed` (always seed — manifestos are small, full rebuild is faster than diffing)

## Risks
- **Lancaster Wmatrix URL stability**: The Lancaster Wmatrix URLs may change or become unavailable. Mitigation: implement fallback to party website PDFs with text extraction. Log the source used for each manifesto.
- **FTS5 table on Android**: FTS5 is available from API 21+ (Android 5.0), but Room's `@Fts4` annotation only supports FTS4. The FTS5 table is created at build time with raw SQL and queried at runtime with raw `@Query`. Mitigation: the FTS4 table (via Room `@Fts4`) is the primary search path; FTS5 is a secondary optimization for API 21+ devices. Plan 11-07 handles the dual-path query logic.
- **FTS virtual table diffing**: `diff_db.py` may not handle FTS virtual tables correctly (they don't have row-level diffs like regular tables). Mitigation: treat manifestos as full-replace in the diff — delete all rows and re-insert. Since there are only 7 rows, this is trivially fast.
- **Manifesto text encoding**: Lancaster Wmatrix TXT files may have encoding issues (BOM, non-UTF-8). Mitigation: explicitly decode as UTF-8 with `errors='replace'` fallback in the build script.
- **DB size increase**: 7 manifestos at ~120K words total (~815KB plain text) plus FTS indexes. Mitigation: the FTS4 index adds ~2-3× the text size. Total DB increase is ~2-3MB, acceptable for the bundled DB.
