# Plan 09-04: CI infrastructure — recess-gated workflows, seed automation, checkpoint/resume, smart delta

**Phase:** 9 (Interests & Income)
**Type:** ci-infrastructure
**Depends on:** 09-01 (build_interests.py must exist for interests workflow; merge_dbs.py must accept 7 DBs for seed automation)

## Objective

Make the goveye-data CI pipeline resilient and efficient: (1) skip unnecessary workflow runs during parliamentary recess, (2) automate the weekly Build Seed, (3) add checkpoint/resume to the 4 expensive seed builds so a crash at item 1001 doesn't lose 1000 fetched items, and (4) optimize Bills delta mode to only fetch stage details for changed bills instead of re-fetching all 4000.

## Tasks

### Task 1: Create `check_recess.py` — shared recess gate script
**File:** `goveye-data/check_recess.py`
**Action:** create
**Description:**

Create a shared Python script that queries the Egg Timer API, checks if today falls within any recess date range for the Commons (houseId=1), and outputs `skip=true` or `skip=false` for GitHub Actions. The script fails open — on any error (API down, parse failure, etc.), it outputs `skip=false` (run the build).

**Script behavior:**
1. Fetch `https://api.parliament.uk/egg-timer/houses/1/recess-dates` (Commons)
2. Parse the HTML to extract recess date ranges (reuse `build_recess.py`'s `parse_recess_dates()` logic — import it or extract to a shared helper)
3. Get today's date (UTC, as `yyyy-MM-dd`)
4. Check if today falls within any recess range (`startDate <= today <= endDate`)
5. Output `skip=true` if in recess, `skip=false` if not
6. On ANY exception: output `skip=false` and exit 0 (fail open — never block a build due to a check failure)

**Output format (GitHub Actions):**
```python
# Writes to stdout for GitHub Actions step output
print(f"skip={'true' if in_recess else 'false'}")
```

**Usage in workflow:**
```yaml
- name: Check if parliament is in recess
  id: recess_check
  run: python check_recess.py
```

**Acceptance:**
- `check_recess.py` fetches Commons recess dates from Egg Timer API
- Returns `skip=true` when today is in a recess range
- Returns `skip=false` when today is not in recess
- Returns `skip=false` on any error (API timeout, parse failure, network error)
- Exits 0 in all cases (never fails the workflow)
- Has unit tests covering: in-recess, not-in-recess, API-down (mock), empty-response

def build_seed(output_path, schema_path, bill_limit=None, checkpoint_db=None):
    timestamp_millis = int(time.time() * 1000)

    if checkpoint_db and os.path.exists(checkpoint_db):
        shutil.copy2(checkpoint_db, output_path)
        conn = sqlite3.connect(output_path)
        max_bill_id = get_max_bill_id(conn)
        logger.info("Resuming from checkpoint: max_bill_id=%d", max_bill_id)
    else:
        conn = schema_module.create_database_with_tables(
            output_path, schema_path, TABLE_NAMES,
        )
        max_bill_id = 0

    bills = fetch_all_bills(bill_limit=bill_limit)
    # Filter to only bills with billId > max_bill_id (for resume)
    if max_bill_id > 0:

    if bills:

        for bill in bills:
            bill_id = bill.get("billId") or 0
            stages = fetch_bill_stages(bill_id)
            if stages:

            time.sleep(API_DELAY)

    conn.commit()
    conn.execute("VACUUM")
    conn.close()

### Task 14: Implement smart delta for Bills — only fetch stage details for changed bills
**File:** `goveye-data/build_bills.py`
**Action:** edit
**Description:**

Optimize Bills delta mode to avoid re-fetching stage details for unchanged bills. Currently, delta mode re-fetches all ~4000 bills + ~4000 stage detail calls. With this optimization, it fetches the list (cheap), upserts all bills (cheap), but only fetches stage details for bills where `lastUpdate` changed.

**Changes:**
1. Add `get_previous_bill_updates(conn)` helper:
```python
def get_previous_bill_updates(conn):
    """Build a dict of {billId: lastUpdate} from the previous DB."""
    cursor = conn.cursor()
    cursor.execute("SELECT id, lastUpdate FROM bills")
    return {row[0]: row[1] for row in cursor.fetchall()}
```
2. Modify `build_delta()`:
```python
def build_delta(output_path, previous_db, schema_path, bill_limit=None):
    timestamp_millis = int(time.time() * 1000)

    shutil.copy2(previous_db, output_path)
    conn = sqlite3.connect(output_path)

    # Build a map of previous bill lastUpdate values
    prev_updates = get_previous_bill_updates(conn)
    logger.info("Delta mode: %d bills in previous DB", len(prev_updates))

    bills = fetch_all_bills(bill_limit=bill_limit)
    if bills:
        # Always upsert all bills (list data is cheap)
        insert_bills(conn, bills, timestamp_millis)

        # Only fetch stage details for changed or new bills
        changed_count = 0
        for bill in bills:
            bill_id = bill.get("billId") or 0
            api_last_update = bill.get("lastUpdate") or ""
            prev_last_update = prev_updates.get(bill_id, "")
            if api_last_update != prev_last_update:
                stages = fetch_bill_stages(bill_id)
                if stages:
                    insert_bill_stages(conn, stages, bill_id, timestamp_millis)
                changed_count += 1
            time.sleep(API_DELAY)

        logger.info("Delta: %d/%d bills had stage detail updates", changed_count, len(bills))

    conn.commit()
    conn.execute("VACUUM")
    conn.close()
    logger.info("Delta build complete: %s", output_path)
```

**Note:** The `bills` table stores `lastUpdate` from the API in the `lastUpdate` column. The `lastUpdated` column (capital D) is our internal timestamp. Make sure the comparison uses the API's `lastUpdate` field, not our `lastUpdated`. Check the column mapping in `map_bill_to_entity()` — the API's `lastUpdate` maps to the `lastUpdate` column in the DB.

**Acceptance:**
- Delta mode fetches all bills (list) but only fetches stage details for bills where `lastUpdate` changed
- New bills (not in previous DB) always get stage details fetched
- Unchanged bills skip the stage detail fetch
- The `diff_db.py` patch is still correct (it diffs old vs new DB)
- API call count drops from ~8000 to ~200 + changed_count
